.. _extending:

--------------------
Extending Roundabout
--------------------

.. contents::
   :local:

This page is for contributors adding physics to the ocean core. It covers
how the state is organised, the recipe for landing a new capability, and
the GPU rules that will otherwise cost you a day.

.. note::

   Per-module and per-procedure API documentation is **not** here. It is
   generated by FORD from the ``!!`` docstrings in the source, and lives on
   its own site. The rule in this project is that nobody hand-maintains a
   parallel prose description of what a module does — that is the copy that
   rots. Document your module in its docstrings.


The composed state
==================

The ocean path has one state object, ``ocean_state_t``, declared in the
driver and passed down by argument. It composes a **slot** per concern: the
barotropic state, the multilayer state, the metrics, the continuity kernel,
Coriolis-advection, the pressure force, each mixing closure, the
diagnostics manager, and so on.

It is a single source of truth, and it is deliberately **not** a global.
Four rules keep it from becoming one.

**1. Handle, not global.** ``ocean_state`` is a subroutine argument. No
module does ``use rdb_ocean_state, only: the_one_state``, and nothing
stashes it in a ``save`` variable. The searchable property is that
``grep -r "save :: .*state" src/`` returns nothing.

**2. Each slot owns its memory.** Every allocation happens in the slot's
``init``, every GPU mapping in its ``enter_data``, every release in
``destroy`` and ``exit_data``. Adding a slot means adding one line to the
parent's init — not editing its internals.

Closures that default off are **gated**: they allocate only when their
``enable`` flag is set, so a plain run pays none of their footprint, which
at scale is multiple gigabytes. The flags are latched in
``init_from_config`` *before* ``init``, so the gate can read them.

**3. Read-mostly across slot boundaries.** Coriolis-advection reads the
barotropic velocity; it does not mutate it. The dynamics driver is the only
thing that mutates prognostic state. Diagnostics read state through the
registry, never the other way round.

**4. MPI only through the wrapper.** Every ``rdb_ocean_*`` module operates
on the local subdomain and is genuinely MPI-agnostic — the same source
compiles single-process or multi-rank. ``grep -rE "use (mpi|mpi_f08)"
src/`` returns empty, enforced by the ``no-mpi-in-rdb`` pre-commit hook.
Communication goes through ``src/comm/``, which has one implementation and
no stub twin; single-rank runs take its local paths.

These rules are what make the state scale as a design: a contributor can
implement one slot without reading the rest of the tree.


Adding a capability
===================

The standing recipe, in order:

**1. A namelist knob, defaulting off.** New physics is off until asked for.
This is not timidity — it is what makes every existing namelist and every
test bit-identical across your change, which in turn is what makes the
change reviewable. If the knob is on by default, every baseline in the
repository moves and nobody can tell your physics from your bug.

Add it to the configuration schema, not just to a derived type: the schema
is the source of truth, it generates the knob documentation, and it is what
makes an unknown key fail loud instead of being ignored.

**2. The kernel, gated on the knob.** Follow the existing slot pattern:
allocate in ``init``, map in ``enter_data``, release in ``destroy`` and
``exit_data``, and wire the slot into the parent's orchestrators.

.. warning::

   **Wire the new slot into** ``ocean_state_enter_data``. A slot that
   allocates but is never mapped still *works* on the host build and still
   *appears* to work on the GPU build — while every kernel touching it
   triggers implicit transfers. The observed cost of that omission has run
   from 150× to 1500×.

**3. An analytical test.** Every analytical test added to this core has
caught a real bug. Find a configuration where you know the answer
independently and assert on that, rather than capturing today's output as a
baseline.

**4.** ``pre-commit run --all`` **and** ``fortitude check``.

**5.** ``ctest``, without ``-j``, green on the GPU build.

**6. One capability per commit, one per pull request.** Smaller changes
review faster and bisect cleanly.

If your change adds, removes or renames a closure, a scheme, a knob or an
extension point, update the affected synthesis documents **in the same pull
request**.

There are recipes for the common cases under ``docs/howto/`` — adding a
boundary condition, a closure, a diagnostic, an equation of state, a
namelist knob, a passive tracer, a vertical coordinate.


GPU rules that bite
===================

The GPU build is ``-gpu=...,mem:separate``. There is **no managed or
unified memory**. Internalise what that means before writing a kernel: the
device has its own address space, and nothing crosses between host and
device unless the code says so.

The consequences are not "it crashes". They are worse than that.

Everything a kernel touches must be device-present
--------------------------------------------------

A ``do concurrent`` or ``!$acc`` kernel gets **no** implicit host-to-device
copies for the arrays you care about. An array that is not mapped is read
or written as stale host memory — silently. The symptoms are a budget that
stays at zero, or a division by an unmapped scratch array yielding NaN,
with no crash and no diagnostic.

Worse: nvfortran *does* emit an implicit ``copyin`` for explicit-shape
dummy arguments. So an unmapped array does not reliably fault — it gives
you a **plausible wrong answer**.

Three rules of thumb:

**Map the scratch companion too.** Before calling a kernel, map every state
object *and* its scratch buffer. Mapping the multilayer state but
forgetting the continuity object leaves the face-thickness buffers
off-device, and the result is NaN.

**Arrays mapped with** ``create`` **carry no host values.** ``enter_data``
attaches them without copying. If you set a value on the host before the
map and expect the device to see it, push it explicitly with
``!$acc update device(...)``.

**Pull results back explicitly.** A host-set input read back after a kernel
needs ``!$acc update self(...)``. Local scratch passed straight to an
implementation routine needs its own ``enter data`` / ``exit data`` pair.

All of these directives are inert no-ops on the host and multicore builds,
so add them unconditionally.

.. warning::

   **A green multicore run proves nothing about device data motion.** A
   test that only ever runs on the host build will pass while being
   thoroughly GPU-broken. Verify on the actual GPU build.

Never map a whole derived type
------------------------------

Do not ``!$acc update self`` or ``copyin`` an **aggregate** derived type
that has allocatable components:

.. code-block:: fortran

   ! WRONG — the aggregate copy overwrites the host component
   ! descriptors with DEVICE addresses.  The next host read of
   ! obj%arr(...) segfaults.
   !$acc update self(obj)

   ! RIGHT — update the component arrays.
   !$acc update self(obj%arr_x, obj%arr_y)

Always name the component arrays.

Explicit-shape dummies in kernels
---------------------------------

Assumed-shape dummy arguments in a ``do concurrent`` kernel make NVHPC walk
the array descriptor with per-launch memory copies. Use explicit shapes:

.. code-block:: fortran

   ! Declare the dimensions BEFORE the arrays that use them --
   ! ifx warns #8586 otherwise.
   integer, intent(in) :: nx, ny, nz
   real(wp), intent(inout) :: arr(nx, ny, nz)

Both rules are enforced by pre-commit hooks (``dc-assumed-shape`` and
``decl-order``). Cadence-bounded code may waive the first with an explicit
``! assumed-shape-ok: <reason>`` comment.

Loop index order
----------------

The contiguous index goes **last** in a ``do concurrent`` header:

.. code-block:: fortran

   do concurrent(k=1:nz, j=1:ny, i=1:nx)

Getting this backwards costs a factor of 16 to 23 on the CPU and OpenMP
paths. It is free to get right.

Clamps launder NaN
------------------

Under nvfortran's relaxed floating-point default — which ``-fast`` implies,
absent ``-Kieee`` — an ``if``/``else`` clamp lowers to a NaN-blind
min/max select:

.. code-block:: fortran

   ! A NaN input comes OUT as lo or hi.
   if (u > hi) then
      u = hi
   else if (u < lo) then
      u = lo
   end if

So a clamp silently converts corruption into a plausible extreme value.
Comparisons with NaN are false, so a guard like ``if (abs(u) > thresh)``
also silently skips NaN rather than catching it.

Any clamp that can see non-finite data must be ``ieee_is_finite``-guarded.
Never rely on a comparison alone to bound corrupted data.

Scratch allocation
------------------

Never allocate scratch inside a per-step kernel on the GPU build — a
per-call allocation stalls the device on entry and exit. Hoist the
workspace onto the state slot so it is mapped once by ``enter_data``.

Escaping arrays pessimise the caller
------------------------------------

A host-gated call that hands a state array to an **external** subroutine
costs even when the branch is never taken. Passing an array as an
``intent(inout)`` actual makes nvfortran treat it as escaping, which
pessimises *every* ``do concurrent`` in the calling routine. This has been
measured at +4.8 % of total solver time for a knob that was switched off.

The fix is to write the guarded operation inline as a ``do concurrent`` in
the same routine. Moving it to a same-module helper does not help — it is
the call that costs, not the module boundary.


Style
=====

* Module files are prefixed ``rdb_``, tests ``test_``. Extension ``.F90``.
* Types end in ``_t``; constants are UPPERCASE; everything else is
  snake_case.
* ``use`` always with ``only:``. ``implicit none``, ``private`` by default,
  explicit ``public``.
* Intrinsic modules need the modifier:
  ``use, intrinsic :: iso_fortran_env, only: ...``.
* No ``print *`` — use the logger.
* **Default new procedures to** ``pure``. Non-pure is the justified
  exception, for I/O, logging, MPI, mutating module state, or a lazy
  allocate.
* Working precision is ``wp`` from ``rdb_constants``.
* FORD docstrings are ``!!`` **after** the declaration.

The full guide is ``FORTRAN_STYLE.md``.


Two constants to get right
==========================

.. list-table::
   :header-rows: 1
   :widths: 20 18 62

   * - Constant
     - Value
     - Use it when
   * - ``H_VANISHED``
     - :math:`1.5\times10^{-4}\ \mathrm{m}`
     - The question is "does this layer matter physically?" A layer this
       thin should be **skipped or merged**, not clamped.
   * - ``H_DIV_EPS``
     - :math:`10^{-20}`
     - The question is "could this denominator be exactly zero?" Pure
       divide-by-zero armour, with no physical meaning.

Both live in ``rdb_constants`` with their roles documented. Choosing the
wrong one produces code that works until it does not.
